01 · System Design

How the system is structured

A single frontend talks to a single backend app over REST and WebSocket. Internally, the backend is split into clearly-bounded modules — the same logical boundaries a microservices version would have — but they run in one process, deploy together, and share one database.

Build pattern used for every module

Single responsibility

Each module owns one business capability only — same rule as microservices, just enforced by code review instead of network boundaries.

Own schema, public interface

A private Postgres schema per module. Other modules never query it directly — only through exported service functions.

In-process events, not direct calls

Modules publish events (e.g. "session.ended") through an in-process emitter, so they stay decoupled the same way they would across a message bus.

One deploy, one process

The whole backend ships as a single container. The worker runs as a second process from the same image — no per-module CI/CD needed yet.

03 · Matching Flow

From online status to a live conversation

Identical logic to a microservices version — the Matching module works off a live Redis pool, not a full-table scan. Only the transport changes: in-process calls instead of network hops.

Why this still scales

ConcernApproach
Finding a match fastOnline users live in a Redis structure keyed by interest tag — O(1) lookups per tag, same as the microservices design.
No match availableUser stays in the pool and is notified over WebSocket the moment a compatible partner comes online — no blocking wait, no polling.
Fair pairingA lightweight ranking step (interest overlap count, wait time) breaks ties so no user waits indefinitely.
Handling more trafficThe whole backend app scales horizontally behind a load balancer (stateless API layer); Redis holds the shared pool state across instances.
Session length — once matched, the Session module starts the room with a 7‑minute or 10‑minute timer (user-selected). At zero, the room closes and an in-process event hands the transcript to the AI Feedback module's queue.

04 · AI at Scale

Handling AI responses without a microservice

This is the one piece worth keeping genuinely asynchronous even in a simple architecture — the burst-load problem is real regardless of scale. It's solved with a queue and a second process, not a separate service.

The core problem

Generating pronunciation and grammar feedback requires speech-to-text plus an LLM pass per session. If the API called the model synchronously on every "session.ended" event, a burst of simultaneous call endings would block API request threads and stall the whole app — even with just one backend.

The solution: same codebase, separate process

Session ends
Transcript + audio ref
→
Redis Queue
BullMQ / Celery job
→
Worker Process
Same repo, own entrypoint
→
Model Inference
Managed STT + LLM API
→
Push to user
WebSocket / notification

Queue every job, never call the model inline

The API route handling "session.ended" only enqueues a job and returns immediately — the user sees "feedback is on its way" instantly.

A worker process consumes the queue

Run as node worker.js (or celery -A app worker) — same codebase, deployed as a second process/container. Concurrency is capped (e.g. 5–20 jobs at once) instead of Kubernetes autoscaling.

Use a managed inference API, not a self-hosted GPU pool

At this size, calling a hosted speech-to-text + LLM API is far cheaper and simpler than running your own batched GPU server — that's the first thing to defer until volume justifies it.

Per-user rate limiting still applies

A cap on concurrent jobs per user in the queue prevents any one user (or bug) from starving everyone else — same rule, enforced in one place instead of a gateway.

Cache common results

Recurring grammar patterns and common mispronunciations are cached in Redis, so the model is only called for what's actually new.

Results are pushed, not polled

When a job completes, the worker writes to Postgres and emits over the same WebSocket gateway the API uses — no separate notification service needed.

05 · Reliability, Stack & Migration Path

Resilient today, splittable tomorrow

One process means fewer moving parts to break — but you still design for graceful failure, and you keep the door open to split out services later.

RiskMitigation
Worker job fails mid-runJobs are re-queued automatically (BullMQ/Celery retry policy); jobs failing after N retries land in a dead-letter queue for review instead of being lost.
Backend instance crashesMultiple stateless app instances behind a load balancer — a crashed instance is restarted/replaced without dropping the whole app.
One module has a bugContained by module boundaries and typed interfaces, but a hard crash can still affect the process — this is the main trade-off vs. microservices, mitigated by good test coverage per module.
Traffic spikesHorizontal autoscaling on the app tier (2–3 instances typical for a launch); worker concurrency scales independently since it's a separate process.
Silent failuresCentralized logging and error tracking (Sentry) across the single app — actually simpler to trace than cross-service logs at this size.

This vs. the microservices version

Modular Monolith (this doc)

  • One deploy, one database, one CI pipeline
  • Ships in weeks, not months
  • Runs on 1–3 small instances + a worker
  • Right fit for 1–3 devs and pre-scale traffic

Microservices (prior doc)

  • Kubernetes, Kafka, DB-per-service, per-service CI/CD
  • Weeks of infra setup before first feature ships
  • Each service scales independently
  • Right fit once a real team and real load exist
Migration path — because module boundaries are already enforced (own schema, public interface only, event-driven communication), moving the AI Feedback or Matching module into its own service later is a matter of adding a network call where an in-process one used to be — not a redesign.
This document focuses on architecture and design decisions, not implementation code. Both frontend and backend can use any language/framework that fits the team, as long as module boundaries and the queue-based AI pipeline above are respected.
