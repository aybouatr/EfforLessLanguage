01 · System Design

How the system is structured

A client-facing gateway routes traffic to independent microservices. Each service owns its own data and talks to the others through APIs and an event bus, so no single service can block the rest of the system.

Every service follows the same pattern: a small, focused responsibility, its own datastore, a versioned API, and independent deployment.

Build pattern used for every service

Single responsibility

Each service owns one business capability only — never split logic across services, never merge two capabilities into one.

Own datastore

A private database per service. Other services never query it directly — only through the service's API.

Versioned API contract

REST or gRPC endpoints, documented and versioned, so one service can change internally without breaking callers.

Containerized & independently deployed

Each service ships as its own Docker image, deployed and scaled on its own schedule via Kubernetes.

03 · Matching Flow

From online status to a live conversation

The Matching Service works off a live pool of online users rather than scanning the full user base on every request.

User comes online
Added to Redis pool with interests
→
Overlap search
Find pool member with shared interest
→
Match event
"match.created" published
→
Session created
Room + timer started

Why this scales

ConcernApproach
Finding a match fastOnline users live in an in-memory Redis structure keyed by interest tag, so lookups are O(1) per tag instead of scanning a SQL table.
No match availableUser stays in the pool and is notified asynchronously the moment a compatible partner comes online — no blocking wait.
Fair pairingA lightweight ranking step (interest overlap count, wait time) breaks ties so no user waits indefinitely.
Independent scalingThe Matching Service scales on its own — a traffic spike in matching never affects Auth or Notifications.
Session length — once matched, the Session Service starts the room with a 7‑minute or 10‑minute timer (user-selected). At zero, the room closes automatically and the transcript is handed to the AI Feedback Service.

04 · AI at Scale

Handling AI responses for many concurrent users

Thousands of calls can end in the same minute. The AI Feedback Service is built so it never blocks a user's app waiting for a model to finish.

The core problem

Generating pronunciation and grammar feedback requires speech-to-text plus an LLM pass per session. If every ended call triggered an inference call synchronously, a burst of simultaneous endings would overload the model and stall the whole app.

The solution: queue, batch, and push

Session ends
Transcript + audio ref
→
Job Queue
One job per session
→
Worker Pool
Auto-scales with queue depth
→
Model Inference
Batched, GPU-backed
→
Push to user
WebSocket / notification

Queue every request instead of calling the model directly

Each finished session becomes a message on a queue (e.g. Kafka/SQS). The app immediately tells the user "feedback is on its way" — nothing waits on the model.

A worker pool consumes the queue

Stateless worker processes pull jobs, call speech-to-text, then the LLM. The number of workers auto-scales up or down based on how deep the queue is.

Requests are batched at the model layer

Instead of one inference call per user, the model server groups several waiting requests into a single batched GPU pass, which uses hardware far more efficiently under load.

Per-user rate limiting and fairness

A cap on concurrent jobs per user prevents any single user (or bug) from starving the queue for everyone else.

Caching common results

Recurring grammar patterns and common mispronunciations are cached, so the model is only asked to analyze what's actually new.

Results are pushed, not polled

When a job completes, the result is pushed to the user over WebSocket (or a notification if offline) rather than the client repeatedly asking "is it ready yet?"

05 · Reliability & Stack

Keeping it resilient under load

Because services are independent, failure in one area shouldn't take down the rest of the platform.

RiskMitigation
AI worker crashes mid-jobJobs are re-queued automatically; failed jobs after N retries move to a dead-letter queue for review instead of being lost.
Matching Service overloadedHorizontal autoscaling on the online-pool size; the gateway applies backpressure before it cascades to other services.
One service goes downCircuit breakers stop callers from repeatedly hitting a failing service; the rest of the app (e.g. login) keeps working.
Sudden traffic spikesKubernetes horizontal pod autoscaling per service, driven by CPU and queue-depth metrics.
Silent failuresCentralized logging, tracing, and metrics (per service) so issues are caught before users notice.
